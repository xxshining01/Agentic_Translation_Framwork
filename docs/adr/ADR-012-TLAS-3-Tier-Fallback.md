# Architecture Decision Record (ADR)

**หมายเลขเอกสาร:** ADR-012
**หัวข้อ:** การใช้สถาปัตยกรรม Rule-Based Taxonomy แบบ 3-Tier Fallback และ Timeline States สำหรับระบบจัดการการแปลบทสนทนา (Dialogue Localization System)
**สถานะ:** อนุมัติ (Accepted)

## 1. บริบทและปัญหา (Context & Problem Statement)

ในการแปลโปรเจกต์เกม RPGM/Ren'Py ที่มีจำนวนคำมหาศาลและมีเส้นเรื่องที่ซับซ้อน ความท้าทายหลักคือการรักษาความคงที่ของ "เสียงและบุคลิกตัวละคร" (Character Voice Consistency) โดยเฉพาะในภาษาไทยที่มีความละเอียดอ่อนเรื่องสรรพนาม ระดับความทางการ และหางเสียง (เช่น การใช้ คะ/ค่ะ ให้ถูกต้องตามหลักไวยากรณ์ หรือการลากเสียงตามอารมณ์)

การเก็บข้อมูลสไตล์การพูดแบบ Hardcode ไว้ใน Character Profile เพียงอย่างเดียว ทำให้เกิดข้อจำกัดดังนี้:

* **ปัญหาความสัมพันธ์:** ไม่สามารถรองรับการสนทนากับตัวละครประกอบ (NPC) หรือคนแปลกหน้าที่ไม่ได้ระบุความสัมพันธ์ไว้ล่วงหน้า
* **ปัญหาการเติบโตของตัวละคร:** ขาดความสามารถในการปรับเปลี่ยนบุคลิกตามเหตุการณ์สำคัญในเส้นเรื่อง (Timeline Progression)
* **ปัญหาอารมณ์ชั่วคราว:** ไม่รองรับการแสดงอารมณ์สุดโต่งในแต่ละบริบทของประโยค (Dynamic Context) เช่น ตัวละครที่สุภาพอาจหลุดคำหยาบเมื่อโกรธจัด
* **ปัญหาข้อมูลดิบ:** โครงสร้างสคริปต์จากเอนจิ้นเกม (Raw Data) ยังมีแท็กคำสั่ง (Control Codes) และรวมชื่อผู้พูดกับข้อความไว้ด้วยกัน ทำให้ประมวลผลอัตโนมัติได้ยาก

## 2. การตัดสินใจ (Decision)

เราตัดสินใจออกแบบสถาปัตยกรรมข้อมูลแบบแยกส่วน (Decoupled Architecture) และสร้าง Pipeline การประมวลผลดังต่อไปนี้:

### 2.1 แยกส่วนข้อมูล (Data Decoupling)

แยกองค์ประกอบของข้อมูลออกเป็น 2 แกนหลัก:

1. **Character Profile (ตัวแปร):** เก็บข้อมูลอัตลักษณ์ (Base Identity), สไตล์การพูดพื้นฐาน (Base Speech Style) และการเปลี่ยนแปลงตามเหตุการณ์ (Timeline States / Delta Modifiers)
2. **Taxonomy & Rules Engine (ฟังก์ชัน):** ไฟล์กลางที่เก็บกฎเกณฑ์ทางภาษา (Grammar Rules) และเงื่อนไขการจับคู่ (Mapping Rules) พร้อมกำหนด `priority_score`

### 2.2 ระบบตรรกะตัดสินใจแบบ 3 ลำดับชั้น (3-Tier Fallback Resolution Logic)

ในการเลือกสรรพนามและหางเสียง ระบบจะตรวจสอบและตัดสินใจตามลำดับความสำคัญ (Priority) ดังนี้:

* **Tier 1: Exact Match (คะแนนสูงสุด):** อ้างอิงจากข้อมูล `relationships` ใน Character Profile หาก ID ของผู้ฟังตรงกับที่ระบุไว้ ให้ใช้สไตล์การพูดเฉพาะบุคคลนั้นทันที
* **Tier 2: Target Condition Match (คะแนนปานกลาง):** หากไม่พบข้อมูลใน Tier 1 ระบบจะวิเคราะห์ลักษณะของผู้ฟัง (เช่น เพศ, ช่วงอายุ) ไปเทียบกับ `target_conditions` ใน Taxonomy เพื่อดึงกฎเกณฑ์ที่เหมาะสมกับสถานะทางสังคม
* **Tier 3: Base Profile Default (คะแนนต่ำสุด):** หากไม่เข้าเงื่อนไขใดเลย ให้กลับไปใช้สรรพนามและสไตล์พื้นฐานจาก `base_speech_style` ของตัวละครนั้น

### 2.3 การจัดการไวยากรณ์ไทยและอารมณ์ (Thai Grammar & Dynamic Overrides)

* **Ending Particles:** กำหนดเพียง Root Word (เช่น "คะ/ค่ะ", "ครับ") ในฐานข้อมูล ส่วนการประกอบร่าง (เช่น "นะคะ", "ไหมคะ") จะขึ้นอยู่กับรูปประโยคบอกเล่าหรือคำถามใน Dialogue
* **Dynamic Tags:** นำแท็กบริบทระดับประโยค (เช่น `EMO_ANGER`, `TON_PLAYFUL`) ไปจับคู่กับ Priority ระดับสูงใน Taxonomy เพื่อแทรกแซงกฎปกติ (Override) และแนะนำการลากเสียง (Vocal Extensions) หรือการใช้คำหยาบ

### 2.4 ท่อส่งข้อมูลและการประมวลผล (Data Processing Pipeline)

ข้อมูลสคริปต์ดิบ (เช่น ไฟล์ `chunk_p1_0000.json`) จะต้องผ่านกระบวนการดังนี้ก่อนนำไปแปล:

1. **Data Extraction & Cleaning:** ใช้ Regex แยก `Speaker_ID` ออกจาก Dialogue และทำ Masking ซ่อน Control Codes (เช่น `\|`, `\fb`) เพื่อป้องกันความผิดพลาดระหว่างแปล
2. **Automated Matching:** ระบบนำข้อมูลที่ทำความสะอาดแล้ว ไปวิ่งผ่าน 3-Tier Fallback Logic เพื่อสร้าง "ไกด์ไลน์ตั้งต้น" ให้กับประโยคนั้นๆ
3. **Human Execution:** นักแปล (มนุษย์) ประเมินไกด์ไลน์ร่วมกับบริบทที่แท้จริง และขัดเกลาอารมณ์ภาษาให้ออกมาสมบูรณ์ที่สุด

## 3. ผลที่ตามมา (Consequences)

### 3.1 ข้อดี (Positives)

* **Scalability:** รองรับสคริปต์ที่มีตัวละครประกอบ (NPC) จำนวนมากได้โดยอัตโนมัติ ไม่ต้องสร้าง Profile ให้ขยะล้นระบบ
* **Consistency & Evolution:** รักษาความสม่ำเสมอของแก่นตัวละครได้ดีเยี่ยม ในขณะที่เปิดช่องให้ตัวละครมีพัฒนาการทางอารมณ์และบุคลิกตามกาลเวลา
* **Efficiency:** สร้างไกด์ไลน์แปลภาษาแบบกึ่งอัตโนมัติ ช่วยลดภาระการจำข้อมูลของนักแปล และลดความผิดพลาดในการใช้สรรพนามผิดบริบท

### 3.2 ข้อจำกัดและความเสี่ยง (Negatives & Risks)

* **Overhead ในช่วงเริ่มต้น:** ต้องใช้เวลาและความพยายามสูงในการทำ Data Parsing (เขียนสคริปต์/Regex) เพื่อคลีนไฟล์สคริปต์เกม และการตั้งค่า Mapping Rules ให้ครอบคลุม
* **การพึ่งพาวิจารณญาณมนุษย์:** แม้ระบบ Rules จะซับซ้อน แต่ขั้นสุดท้ายในการเลือกใช้รูปประโยคไวยากรณ์ไทยที่สละสลวย (เช่น คะ/ค่ะ) และบริบทอารมณ์แฝง ยังคงต้องอาศัยวิจารณญาณจากนักแปลเป็นผู้ตัดสินขั้นเด็ดขาด

## 4. สถานะความสอดคล้องกับมาตรฐาน (Compliance)

สถาปัตยกรรมนี้รองรับการขยายตัวระดับโปรเจกต์ขนาดใหญ่ (AAA/Large Scale Text) โดยแยก Data Structure กับ Business Logic (Rule Engine) ออกจากกันอย่างเด็ดขาด ตรงตามหลักการออกแบบซอฟต์แวร์ที่ดี (Separation of Concerns)
