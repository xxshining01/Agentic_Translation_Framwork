# ADR-004: Memory Architecture

**Status:** Proposed
**Date:** 2026-07-09
**Decision Maker:** Product Owner + AI Solution Architect

---

## 1. Context and Problem Statement

ในการแปลเกมหรือนิยายที่มีขนาดยาว (เช่น เกม RPG หรือ Visual Novel) บริบทที่เกี่ยวข้องจะมีมหาศาล ทั้งข้อมูลตัวละครนับสิบตัว ศัพท์เฉพาะ สถานที่ และเนื้อเรื่องที่ผ่านมา หากเราใช้วิธีนำข้อมูลทั้งหมดนี้ยัดลงไปใน Prompt เดียว (Context Stuffing) จะเกิดปัญหาดังนี้:

1. **Lost in the Middle:** โมเดล LLM มักจะลืมข้อมูลที่อยู่ตรงกลางของ Prompt และให้ความสำคัญเฉพาะส่วนหัวและส่วนท้าย
2. **Hallucination & Cross-contamination:** AI อาจเอาลักษณะนิสัยของตัวละคร A ไปผสมกับตัวละคร B เพราะข้อมูลอยู่ใน Prompt เดียวกัน
3. **Token Inefficiency:** สิ้นเปลืองค่าใช้จ่าย (Token) ไปกับข้อมูลที่ไม่ได้ใช้ในประโยคปัจจุบัน

## 2. Decision

เราตัดสินใจใช้ **Layered & Segregated Memory Architecture (สถาปัตยกรรมหน่วยความจำแบบแยกส่วนและแบ่งชั้น)** แทนที่การโยนข้อมูลทั้งหมดให้ AI

ระบบจะเก็บข้อมูลแยกออกจากกันอย่างเด็ดขาดเป็น 5 ฐานข้อมูล (Domains) และ Agent จะได้รับอนุญาตให้เห็น "เฉพาะเศษเสี้ยวข้อมูล (Fragments)" ที่จำเป็นต่อ Batch นั้นๆ ผ่านกระบวนการ Dynamic Prompt Assembly ที่จัดการโดย Python

### Memory Domains

1. **Character Memory:**
* เก็บข้อมูลลักษณะนิสัย สรรพนามที่ใช้เรียกตัวเอง/คนอื่น (Pronouns & Honorifics) และความสัมพันธ์
* *การดึงข้อมูล:* ดึงมาเฉพาะตัวละครที่กำลังพูดใน Batch นั้น หรือตัวละครที่ถูกพูดถึง (Mentioned)


2. **Story Memory:**
* เก็บสรุปเหตุการณ์ (Summarization) ของเนื้อเรื่องที่ผ่านมา เพื่อให้ AI เข้าใจสถานการณ์ปัจจุบัน
* *การดึงข้อมูล:* ดึงเฉพาะบริบทของ Chapter หรือ Scene ปัจจุบัน


3. **Glossary Memory:**
* คลังคำศัพท์เฉพาะ ชื่อสถานที่ ชื่อไอเทม ท่าไม้ตาย
* *การดึงข้อมูล:* Python จะสแกนหา Keyword ในประโยคต้นทาง และดึงเฉพาะคำศัพท์ที่พบใส่ลงไปใน Prompt


4. **Translation Memory (TM):**
* เก็บประโยคที่เคยแปลไปแล้วและได้รับการอนุมัติ เพื่อรักษาความคงเส้นคงวา (Consistency) ของประโยคที่ซ้ำกัน
* *การดึงข้อมูล:* Python จะใช้ Exact Match หรือ Fuzzy Search หากพบประโยคที่ตรงกันสูง จะข้ามการแปลของ AI ไปเลย หรือให้ AI อ้างอิงเป็นหลัก


5. **Project Memory:**
* กฎเกณฑ์ของโปรเจกต์ เช่น รูปแบบการเว้นวรรค กฎการใช้สัญลักษณ์



## 3. Rationale

การทำงานแบบ "Need-to-Know Basis" (ให้รู้เท่าที่จำเป็นต้องใช้) จะช่วยลดปริมาณ Token ในแต่ละ Request ลงอย่างมหาศาล ทำให้โมเดลสามารถโฟกัสกับคำสั่งตรงหน้าได้อย่างเต็มประสิทธิภาพ ลดความสับสนของ AI (Cognitive Overload) และช่วยให้มั่นใจว่าคำศัพท์เฉพาะจะไม่ตีกันเอง

## 4. Consequences

**Pros (ข้อดี):**

* ความแม่นยำในการรักษาคาร์แรคเตอร์และการใช้คำศัพท์สูงขึ้นมาก
* ประหยัดค่า API Token เนื่องจาก Prompt มีขนาดกะทัดรัด
* สามารถสลับไปใช้ LLM ที่มี Context Window ขนาดเล็ก (แต่ฉลาด) ในบางขั้นตอนได้

**Cons (ข้อเสีย):**

* ฝั่ง Python ต้องรับภาระหนักในการเขียนระบบสืบค้นข้อมูล (Retrieval System) เช่น การทำ Keyword Matching สำหรับ Glossary หรืออาจต้องใช้ Vector Database ในกรณีที่เนื้อเรื่องมีความซับซ้อนสูง
