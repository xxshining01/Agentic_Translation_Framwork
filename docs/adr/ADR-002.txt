# ADR-002: End-to-End System Workflow

**Status:** Proposed
**Date:** 2026-07-09
**Decision Maker:** Product Owner + AI Solution Architect

---

## 1. Context and Problem Statement

หลังจากที่เราตกลงใช้ Multi-Agent Architecture ใน ADR-001 คำถามต่อมาคือ "ข้อมูลจะไหลผ่านระบบอย่างไร" การแปลไม่ใช่ขั้นตอนเดียว (Single Step) แต่เป็นกระบวนการผลิต (Production Pipeline)

หากเรียงลำดับการทำงานผิดพลาด เช่น ให้ AI ใส่สัญลักษณ์ Timing ก่อนที่จะผ่านกระบวนการ QA หาก QA ตรวจพบว่าประโยคไม่เป็นธรรมชาติและสั่งเขียนใหม่ สัญลักษณ์ Timing ทั้งหมดที่ทำไว้จะพังทลายทันที ดังนั้นเราต้องการ Workflow ที่มีตรรกะรองรับในทุกๆ ขั้นตอน และต้องแยกระหว่างงานของ Python (Deterministic) และ AI (Semantic) อย่างชัดเจนตามที่ระบุไว้ใน ADR-000 

## 2. Decision

เราตัดสินใจใช้ **Linear Event-Driven Pipeline** โดยแบ่งแยกสถานะ (Stages) การทำงานอย่างเด็ดขาด ข้อมูลจะไหลไปข้างหน้าแบบทิศทางเดียว (Unidirectional Data Flow) เว้นแต่จะเกิดข้อผิดพลาด จึงจะตีกลับในรูปแบบของ Repair Loop

### System Workflow (The Pipeline)

```text
[1] Ingestion & Parsing (Python)
        ↓
[2] Batching & Context Assembly (Python + Executive Logic)
        ↓
[3] Translation (AI)
        ↓
[4] Editing & Emotion (AI)
        ↓
[5] Consistency & Glossary (Python + AI)
        ↓
[6] Quality Assurance / QA (AI)
        ↓
[7] Timing & Formatting (AI + Python)
        ↓
[8] Final Validation (Python)
        ↓
[9] Assembly & Export (Python)

```

## 3. Rationale (เหตุผลทางวิศวกรรมของแต่ละขั้นตอน)

* **[1] Ingestion & Parsing (ทำไมต้องเริ่มด้วย Python):**
ไฟล์เกมมีโครงสร้างเฉพาะ (เช่น Ren'Py, JSON) Python ต้องแกะเอาเฉพาะ "ข้อความที่ต้องแปล" ออกมา และทิ้งโครงสร้างโค้ดไว้ข้างหลัง AI จะต้องไม่เห็นโค้ดเอนจินเกมเพื่อป้องกัน Hallucination 


* **[2] Batching & Context Assembly:**
ก่อนเริ่มแปล ระบบต้องเตรียม Translation Memory (TM), Glossary และข้อมูลตัวละคร (Character Memory) ที่เกี่ยวข้องกับประโยคชุดนั้นๆ มาประกอบเป็น Prompt 


* **[3] Translation (ทำไมต้องแยกจาก Editor):**
Translator Agent มีหน้าที่เดียวคือ "รักษาความหมายดั้งเดิมให้ถูกต้องที่สุด" ยังไม่ต้องสนใจความสวยงามมากนัก เพื่อลดภาระการคิด (Cognitive Load)
* **[4] Editing & Emotion (ทำไมต้องอยู่หลัง Translator):**
เมื่อความหมายถูกต้องแล้ว Editor Agent จะนำประโยคมาเกลาให้เป็นธรรมชาติ ปรับน้ำเสียง (Tone) ให้ตรงกับคาร์แรคเตอร์ตัวละคร การแยกสองขั้นตอนนี้ช่วยให้ได้ภาษาไทยที่สละสลวยโดยความหมายไม่ผิดเพี้ยน
* **[5] Consistency & Glossary (ทำไมต้องคั่นกลางก่อน QA):**
ระหว่างที่ Editor เกลาภาษา อาจมีการเผลอเปลี่ยนคำศัพท์เฉพาะหรือสรรพนาม ขั้นตอนนี้ (ใช้ทั้ง Python ตรวจคำและ AI ตรวจบริบท) จะบังคับให้กลับมาใช้คำตาม Glossary ก่อนส่งงานต่อ
* **[6] Quality Assurance (ทำไม QA ถึงไม่อยู่ท้ายสุด):**
QA ทำหน้าที่ประเมิน KPI (Naturalness, Meaning Preservation)  หากประโยคไม่ผ่าน QA อาจมีการสั่งให้ Editor เขียนใหม่ หากเราเอา QA ไว้หลัง Timing การเขียนใหม่จะทำให้ Timing พัง


* **[7] Timing & Formatting (ทำไมต้องทำเกือบสุดท้าย):**
สัญลักษณ์จำพวก `✎`, `|`, `.` เป็นการกำหนดจังหวะการอ่าน (Narrative Timing) จะถูกแทรกเข้าไปก็ต่อเมื่อ "ข้อความภาษาไทยนิ่งแล้วและจะไม่มีการแก้ไขอีก" AI จะเป็นคนกะจังหวะ และ Python จะเป็นคนเช็คว่าสัญลักษณ์ครบถ้วนหรือไม่ 


* **[8] Final Validation (ทำไมด่านสุดท้ายต้องเป็น Python):**
Python จะทำการตรวจสอบเชิงโครงสร้างครั้งสุดท้าย เช่น ตัวแปร (Variables) อยู่ครบไหม ความยาวบรรทัดเกินกำหนดไหม Python จะเป็นผู้ตัดสินชี้ขาด ไม่ใช่ AI 


* **[9] Assembly & Export:**
นำข้อความที่แปลและผ่านการตรวจสอบแล้ว ยัดกลับเข้าไปในโครงสร้างไฟล์ต้นฉบับอย่างปลอดภัย

## 4. Consequences

**Pros:**

* แต่ละ Agent มีเป้าหมายที่ชัดเจนมาก ทำให้เราสามารถปรับจูน Prompt ของแต่ละตัวได้ง่าย
* ข้อผิดพลาดจะถูกดักจับได้ตรงจุด (เช่น ถ้ารูปประโยคแข็งไป คือความผิดของ Editor, ถ้าศัพท์ผิด คือความผิดของ Consistency)

**Cons:**

* ระยะเวลาในการรัน (Execution Time) ต่อ 1 Batch จะนานขึ้นพอสมควรเมื่อเทียบกับการให้ AI ตัวเดียวทำรวดเดียวจบ
* จำเป็นต้องมีการออกแบบ Data Contract (ADR-005) ที่แข็งแรงมาก เพื่อให้ข้อมูลที่ส่งผ่านระหว่างขั้นตอน (Stage) ไม่ตกหล่น
