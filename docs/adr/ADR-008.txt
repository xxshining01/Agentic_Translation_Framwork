# ADR-008: Validation and Repair Loop

**Status:** Proposed
**Date:** 2026-07-09
**Decision Maker:** Product Owner + AI Solution Architect

---

## 1. Context and Problem Statement

ตามที่ระบุไว้ใน ADR-000 ว่า LLM เป็นระบบความน่าจะเป็น (Probabilistic) และไม่สามารถรับประกันความถูกต้องได้ 100% ปัญหาที่มักพบในการแปลไฟล์เกมคือ:

1. **Syntax Destruction:** AI เผลอแปลหรือลบแท็กคำสั่งทิ้ง เช่น การแปลคำสั่ง `image` ใน Ren'Py กลายเป็นภาษาไทย หรือทำวงเล็บตัวแปร (Variables) หล่นหาย
2. **Context Hallucination:** AI แต่งเรื่องเพิ่ม หรือใช้คำหยาบคาย/ผิดบริบท
3. **Pipeline Waste:** หากพบข้อผิดพลาดในขั้นตอน QA หรือ Timing การเริ่มต้นแปลใหม่ตั้งแต่ Translator จะทำให้สูญเสีย Token และเวลาโดยใช่เหตุ

เราต้องมีกลไกตรวจสอบและซ่อมแซมที่ไม่ส่งผลกระทบต่อประสิทธิภาพการทำงานโดยรวม

## 2. Decision

เราตัดสินใจใช้สถาปัตยกรรม **Multi-Layered Validation (การตรวจสอบหลายชั้น)** ควบคู่กับ **Localized Repair Loop (การซ่อมแซมเฉพาะจุด)** 1. **Deterministic Validation (Python):**

* ใช้ Python และ Regex เป็นผู้คุมกฎขั้นเด็ดขาด (Gatekeeper)
* ตรวจสอบว่าแท็กโค้ด ตัวแปร และโครงสร้าง (Formatting) ใน `original_text` ยังคงปรากฏอยู่ใน `final_output` ครบถ้วนตามตำแหน่งที่ควรจะเป็น
* หาก Python ตรวจพบว่าโครงสร้างพัง (เช่น ดักจับเจอว่า AI พยายามแปลคำสั่งระบบ) จะปรับสถานะเป็น `Failed` ทันทีโดยไม่ต้องรอให้มนุษย์ตรวจ

2. **Semantic QA Validation (AI):**
* ใช้ QA Agent ประเมินความหมาย ความเป็นธรรมชาติ และการรักษาคาร์แรคเตอร์


3. **Localized Repair (การซ่อมแซมระดับ Node):**
* เมื่อเกิดข้อผิดพลาด (Error Event) ระบบจะไม่เริ่มต้นกระบวนการใหม่ทั้งหมด
* Event Bus (จาก ADR-006) จะส่ง Payload กลับไปยัง Agent ที่รับผิดชอบ **พร้อมกับระบุข้อผิดพลาดที่ชัดเจน** (Targeted Feedback)
* *ตัวอย่าง:* หาก Timing Agent ใส่สัญลักษณ์ `✎` ผิดที่ ระบบจะวนลูปกลับไปที่ Timing Agent เท่านั้น โดย Editor และ Translator จะไม่ถูกเรียกใช้งานซ้ำ



## 3. Rationale

การแยกระหว่างการตรวจสอบโค้ด (Python) และการตรวจสอบภาษา (AI) เป็นการใช้เครื่องมือให้ตรงกับจุดแข็งของมันมากที่สุด การให้ Python เป็นผู้ตรวจสอบ Regex โครงสร้างขั้นสุดท้าย เป็นการการันตี 100% ว่าไฟล์ที่ถูก Export ออกไปจะไม่ทำให้เอนจินเกม Crash (Code Integrity)

นอกจากนี้ การซ่อมแซมเฉพาะจุด (Localized Repair) ยังตอบโจทย์เรื่องความประหยัดและรวดเร็ว แทนที่จะโยนงานทิ้งทั้ง Batch เราเพียงแค่ซ่อมเฉพาะชิ้นส่วนที่แตกหักในระดับประโยคเท่านั้น

## 4. Consequences

**Pros (ข้อดี):**

* **Fail-Safe Integrity:** มั่นใจได้ว่าไฟล์ปลายทางสามารถนำไปรันในเอนจินเกมได้ทันทีโดยไม่ต้องแก้บั๊กโครงสร้าง
* **Cost Efficiency:** ประหยัดค่า API อย่างมีนัยสำคัญ เพราะซ่อมเฉพาะ Agent ที่ทำงานพลาด
* **Self-Healing:** ระบบสามารถพยายามแก้ไขตัวเองได้ตามจำนวนรอบ (Max Retries) ที่กำหนดไว้

**Cons (ข้อเสีย):**

* ต้องพัฒนาฝั่ง Python ให้มี Regex และ Validation Logic ที่ครอบคลุมทุก Edge Case ของเอนจินเกมนั้นๆ
* หากตั้งค่า Max Retries สูงเกินไป และ AI ไม่สามารถแก้บั๊กได้ (เช่น ติดลูปการแปลผิดแบบเดิมๆ) อาจทำให้เกิด Infinite Loop หรือเสีย Token ฟรี จำเป็นต้องมีกลไก Circuit Breaker เพื่อหยุดการทำงานเมื่อพยายามซ้ำหลายรอบเกินไป

## [UPDATE: 2026-07-18] Evolution of SAFETY_RULE
**Rationale for Update:**
แม้จะมี Python คอยตรวจสอบ (Validation) แต่เราพบว่า AI มักจะทำโค้ดพังตั้งแต่ต้นทาง (เช่น ลบโค้ดทิ้ง หรือคืนค่าเป็นภาษาอังกฤษเหมือนเดิมเพราะกลัวกฎห้ามแตะโค้ด) เราจึงปรับเปลี่ยนรูปแบบของ `SAFETY_RULE` ใน Prompt จากการห้ามดื้อๆ เป็นการอธิบายแนวคิด "Transparent Wrappers" (มองโค้ดเป็นกล่องใส) พร้อมกับให้ **ตัวอย่างที่เป็นรูปธรรม** (เช่น `\fbStop` -> `\fbหยุดนะ`) เพื่อสอนให้ AI รู้จักวิธีแปลข้อความที่อยู่ติดกับโค้ดโดยยังคงรักษาตำแหน่งโค้ดไว้ที่เดิม
