# Software Architecture Document (SAD)

**Project:** Agentic Translation Framework (ATF)
**Phase:** 2 - Architecture Definition
**Status:** Draft

---

## 1. System Overview (ภาพรวมของระบบ)

Agentic Translation Framework (ATF) เป็นระบบซอฟต์แวร์สถาปัตยกรรมแบบกระจายศูนย์ (Decentralized Multi-Agent System) ที่ออกแบบมาเพื่อการแปลภาษา (Localization) สำหรับเกม (เช่น Ren'Py, RPG Maker, Godot) และนิยาย

เป้าหมายหลักของระบบคือการผสานการทำงานระหว่าง **Deterministic Logic (Python)** ที่รับประกันความถูกต้องแม่นยำของโครงสร้างโค้ด 100% และ **Semantic Processing (AI Agents)** ที่รับผิดชอบด้านความสละสลวยทางภาษาและบริบท โดยระบบทำงานแบบ Event-driven เพื่อรองรับ Concurrency และมีกลไกตรวจสอบความถูกต้องด้วยตัวเอง (Self-Validation & Repair)

---

## 2. High-Level Architecture (สถาปัตยกรรมระดับสูง)

ระบบถูกแบ่งออกเป็น 4 เลเยอร์หลัก (Layers) เพื่อให้เกิดการแยกส่วนประกอบที่ชัดเจน (Decoupling) ตามหลักการที่กำหนดไว้ในเอกสาร ADR-003

### Layer 1: Input/Output & Parsing Layer (ชั้นจัดการไฟล์และโครงสร้าง)

รับผิดชอบการอ่านไฟล์ต้นฉบับ แกะโครงสร้าง และประกอบไฟล์กลับเมื่อแปลเสร็จ

* **Engine-Specific Parsers:** โมดูลแยกตามประเภทไฟล์ (เช่น `renpy_parser`, `rpgmaker_parser`, `json_parser`, `csv_parser`)
* **Regex Filter Engine:** ระบบคัดกรองขั้นสูง ทำหน้าที่แยกแยะแท็กโค้ด คำสั่งระบบ (เช่น คำสั่งแสดงภาพ `image` ใน Ren'Py) และตัวแปร (Variables) ออกจากข้อความที่ต้องแปล เพื่อป้องกันไม่ให้ถูกส่งไปยัง AI

### Layer 2: Orchestration & Event Layer (ชั้นควบคุมและสายพานข้อมูล)

หัวใจหลักของการควบคุม Workflow (ADR-002) ทำงานแบบ Asynchronous

* **Event Bus / Message Broker:** ระบบคิวสำหรับรับ-ส่ง Event Payload (เช่น `TranslationCompleted`, `ValidationFailed`) ระหว่างโมดูลต่างๆ
* **State Machine:** ตัวจัดการสถานะของประโยค (Pending, In-Progress, QA-Failed, Done)
* **Dynamic Prompt Assembly (Context Engine):** เครื่องจักรสำหรับดึงข้อมูลจาก Memory Layer (Glossary, Character) มาประกอบเป็น Prompt ชั่วคราว (JIT) เพื่อบังคับเรื่อง Consistency ก่อนยิง API

### Layer 3: Agent Swarm Layer (ชั้นปัญญาประดิษฐ์)

กลุ่มของ AI Agent ที่มีหน้าที่เฉพาะตัว ทำงานผ่าน API ของ LLM Providers (อิงตาม ADR-003)

* **Translator Agent:** แปลความหมายให้ถูกต้องและครบถ้วน
* **Editor Agent:** เกลาภาษา ปรับ Tone/อารมณ์ และถูกบังคับให้ใช้คำศัพท์ตรงตาม Glossary จาก Context Engine
* **Consistency Agent:** ตรวจสอบและบังคับใช้คำศัพท์เฉพาะจาก Glossary
* **QA Agent:** ประเมินคุณภาพตาม KPI (ความหมาย, ความเป็นธรรมชาติ, คาร์แรคเตอร์)
* **Timing Agent:** กำหนดจังหวะการเล่าเรื่องและแทรกสัญลักษณ์ (เช่น `✎`, `|`, `.`)

### Layer 4: Memory & State Storage Layer (ชั้นความจำและฐานข้อมูล)

แหล่งเก็บข้อมูลระยะยาวและบริบทของโปรเจกต์ (ADR-004) สามารถใช้ฐานข้อมูลเช่น Supabase/PostgreSQL สำหรับจัดการ Data Types ที่ซับซ้อน

* **Character DB:** ข้อมูลตัวละคร สรรพนาม และลักษณะนิสัย
* **Glossary DB:** คลังคำศัพท์เฉพาะ
* **Translation Memory (TM):** ประวัติการแปลประโยคที่ผ่านการอนุมัติแล้ว
* **Story State:** สรุปเนื้อเรื่องและเหตุการณ์ตามบริบทปัจจุบัน

## 3. Data Flow Architecture (เส้นทางการไหลของข้อมูล)

การทำงานของ 1 Batch (หรือ 1 ประโยค) จะมีเส้นทางดังนี้:

1. **Ingestion:** ไฟล์ต้นฉบับเข้าสู่ `Parser Layer` ➔ แยกโค้ดออกจากข้อความ ➔ ห่อข้อความเป็น JSON Payload (`TranslationToken`)
2. **Dispatching:** JSON Payload ถูกส่งเข้า `Event Bus` ➔ State เริ่มต้นคือ `PENDING`
3. **Assembly:** `Context Engine` ตรวจจับ Event ➔ ดึง Context (Glossary, Character) จาก `Memory Layer` มาประกอบเป็น Prompt
4. **Processing:** Prompt ถูกส่งเข้า `Agent Swarm Layer` ตามลำดับ (Translator ➔ Editor ➔ Consistency ➔ QA)
5. **Repair Loop:** หาก QA Agent ไม่ให้ผ่าน (Fail KPI) หรือ Validator ตรวจพบโครงสร้างพัง Event จะถูกตีกลับไปยัง Agent ต้นทางพร้อม Error Message
6. **Finalization:** เมื่อผ่าน QA ➔ เข้าสู่ `Timing Agent` ➔ ส่งเข้าตัวตรวจสอบโค้ดด้วย Python (`SyntaxValidator`)
7. **Export:** `Parser Layer` ประกอบข้อความกลับเข้าไฟล์เกม

## 4. Technology Stack (Proposed)

* **Core Engine:** Python 3.11+ (เน้น Asyncio สำหรับ Concurrency)
* **LLM Integration:** LiteLLM หรือ LangChain (เพื่อทำ Abstraction ให้สามารถสลับใช้ OpenAI, Gemini, Claude, Local LLM ได้อย่างอิสระตาม ADR-000)
* **Database & Memory:** * Relational DB (เช่น SQLite สำหรับ Local หรือ Supabase/PostgreSQL สำหรับ Cloud) เพื่อเก็บ State และ Glossary
    * Vector Store (ตัวเลือกเสริมสำหรับค้นหา Story Memory และ TM)
* **Message Queue:** In-memory Async Queue (สำหรับ Local) หรือ Redis (หากต้องการ Scale)
